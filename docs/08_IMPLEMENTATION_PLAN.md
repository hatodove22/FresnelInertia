## Current focus

Turn the encouraging integrated prototype into a repeatable, convincing
demonstration of moving contents. The next gain is not another engine or a
larger preset catalogue: it is a reliable combined experience, useful selected
settings, and clear evidence about what the user can actually feel.

Keep the accepted baseline available. No current software-only result closes
a physical check, and no tuning session establishes a general research claim.

### 1. Restore a dependable exhibition flow

Upload only the affected integrated AtomS3 image when the user resumes hardware
work. Gain tuning and the current servo fixes need no new StampC5 image.
Preserve ordinary powered, supervised testing; do not actuate unattended hardware.

Use one short handling sequence to check the observed fault and any catch-up
feel. Keep Stop and bounded recovery working. If a fault persists, record the
action and relevant state, repair that cause, then repeat the affected portion.
Do not add a long soak, pose matrix or more conservative stimulus limits without
an observed reason. Use [07](07_TEST_AND_VALIDATION.md) for the acceptance boundary.

### 2. Tune the whole sensation

Use the existing [preference workspace](../webxr/README.md#preference-tuning),
not independent vibration and tilt optimizations. Keep a material, fill,
container, grasp and reference gesture fixed within a session. All five
effective coordinates vary as one candidate; the parameter meanings are in
[06](06_PARAMETER_MODEL.md#joint-preference-search).

Hold the device in the right hand; use Q/W to present and A/D/S/X to answer
with the left. Compare in short useful batches, then revisit the selected
candidate against the starting setting. No fixed number of answers establishes
convergence. Record what improved or remained wrong, not just which was stronger.

Use separate sessions for the three representatives. Save a selected profile
for later use. Cross-material reuse transfers only common gains as a new
starting point, never prior votes or an assumption of equal realism.
Software rehearsal remains separate from actual tactile judgments.

### 3. Check the selected experience with the screen

Return the selected settings to the ordinary demo and compare the same motion
with visuals and optional speaker sound. Preserve approved material appearance
and recorded-water sound. Check only the changed flow on the actual Android
phone; do not repeat general phone bring-up or make AR a prerequisite.

Specific items to revisit, not automatic redesign requests:

- Does a water/marble/sand difference remain legible beyond overall intensity?
- Do settling, apparent load and contact timing feel like one object?
- Does visual coin turnover or other 3D presentation disagree with the reduced
  haptic model? Adjust the presentation or identify the actual model gap.
- The reported missing sound during fore/aft-only motion needs a focused
  reproduction and source-routing decision. Do not silently drive new haptic
  collisions from independent visual contacts.
- Judge the sharper soda pop/recoil and revised soda/sand presentation when
  handled; prior approval does not automatically cover those later changes.

A preferred exploratory setting is not yet a held-out evaluation. If a
publication claim about the combined method is next, define the comparison
and evidence separately using [07](07_TEST_AND_VALIDATION.md); do not build a
study-management platform or force separate-branch tuning into this workflow.

## Later choices — not current completion gates

### Separate expressive demo: heartbeat (planned, not implemented)

A fictional heart-like object could combine a main/softer second pulse,
slower fingertip-plane motion and visible contraction. It is a separate
expressive demonstration of coordinated cues, not another gain-calibration
condition or a biometric/medical simulation.

Implement a named shared C++ pulse state if this is selected next; route it
through the existing output boundaries. Do not disguise pulses as collisions
or give the browser an independent beat clock. Existing v4 telemetry is full,
so define compatible state/bridge support before physical deployment. Preserve
ordinary presets and use their existing output bounds. Detailed initial
considerations are in the [dated plan](archive/2026-09-08/08_ACTIVE_PLAN_SNAPSHOT.md#separate-expressive-demo-heartbeat-planned-not-implemented).

### Conditional model and presentation work

- Dynamic-CG refinement: the mapping already exists. Change it only for a
  demonstrated felt mismatch, with the accepted law retained as a comparison.
  [06](06_PARAMETER_MODEL.md) owns current meanings; [model research](reference/34_FW_MODEL_RESEARCH.md)
  contains dated alternatives, not required work.
- Richer fore/aft sand behavior: distinguish a visual surface detail from new
  retained mass/CoG dynamics. A true model extension needs coherent consumers.
- Bouba/Kiki-style tuning shapes: optional interface idea, not a validated
  universal mapping or an implicit change of container geometry.
- Android hand-following AR: optional; hand position and device IMU orientation
  have different roles. A marker is optional alignment, not the primary tracker.
  Quest/VR completion remains deferred.
- The [interaction atlas](reference/32_INTERACTION_DESIGN_SPACE.md) is a library
  of proposals, not twelve milestones. Heartbeat does not require implementing it all.

Formal psychophysics, measured grip feedback, automatic resonance fitting,
recorder/replay recovery, OTA, new transports and cloud/account infrastructure
remain deferred unless a concrete next objective calls for them.
